# QUY TẮC LÀM VIỆC CHO MỌI PROMPT HARDENING

## Dự án
Chợ Pass Sinh Viên: Next.js 14 (App Router) + TypeScript + Tailwind; Firebase (Client SDK: Auth, Storage; Admin SDK: Firestore trong Route Handlers); Vitest; deploy Vercel. Chợ đồ cũ C2C cho sinh viên: chỉ SV đã được duyệt mới đăng tin và xem liên hệ người bán. Production chưa có dữ liệu thật.

## Nguồn của các phát hiện
Một bản review bên ngoài đã đọc README, firestore.rules, storage.rules, next.config.mjs và HTML trang live, nhưng KHÔNG đọc được src/. Vì vậy mọi phát hiện chỉ là GIẢ THUYẾT: luôn đọc code thật trước khi sửa. Nếu phát hiện sai hoặc đã được xử lý → ghi "Không áp dụng" kèm bằng chứng (file:dòng) rồi bỏ qua.

## Luật bắt buộc
1. Nhánh làm việc: `hardening/all` (Prompt 0 tạo). Mỗi prompt tạo các commit riêng, message dạng `hardening(pN): ...`. Không force-push, không rewrite lịch sử.
2. KHÔNG chạy `firebase deploy`, `gcloud`, `vercel`; KHÔNG đọc/ghi/commit secret hoặc .env thật. Việc cần quyền cloud/Vercel → ghi vào "Việc chủ dự án tự làm".
3. Không đổi stack, không nâng major version thư viện, không đổi tên route/collection nếu prompt không yêu cầu. Thêm dependency chỉ khi thật sự cần và ghi lý do.
4. Gate sau mỗi prompt phải xanh: `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run build`; từ Prompt 1 thêm `npm run test:rules`. Test cũ không được hỏng; nếu hành vi đổi có chủ đích thì sửa test và ghi lý do. Gate đỏ thì sửa tới khi xanh; không tắt test/lint để qua; không commit trạng thái đỏ.
5. Mỗi thay đổi bảo mật phải có test chứng minh: viết test trước, thấy fail, sửa, thấy pass.
6. Quyết định chính sách chưa rõ: chọn phương án an toàn nhất mà KHÔNG phá hành vi hiện có, ghi vào "Quyết định cần chủ dự án xác nhận". Không hỏi giữa chừng.
7. Không bịa số liệu (hiệu năng, độ phủ test...). Không đo được thì nói rõ là không đo được.
8. Việc ngoài phạm vi prompt: không sửa, chỉ ghi vào "Phát hiện thêm".
9. Không log PII (MSSV, ảnh thẻ, SĐT/Zalo, email); không đưa PII thật vào thông báo lỗi hay test fixture.
10. Thông báo hướng người dùng viết bằng tiếng Việt có dấu, ngắn gọn, không đổ lỗi cho người dùng.

## Báo cáo
Cuối mỗi prompt, thêm một mục vào `docs/HARDENING_REPORT.md` (tạo nếu chưa có) gồm: Đã làm · Không áp dụng (+bằng chứng) · File đã đổi · Test đã thêm · Việc chủ dự án tự làm · Quyết định cần xác nhận · Phát hiện thêm · Kết quả các gate. Cuối phiên, trả lời người dùng tối đa 10 dòng tóm tắt.
Đọc và tuân thủ tuyệt đối `docs/HARDENING_RULES.md`. Nếu file không tồn tại, dừng và báo người dùng.

# PROMPT 0 — Audit & xác minh giả thuyết (CHỈ ĐỌC, KHÔNG SỬA CODE)

## Mục tiêu

## Các bước

# PROMPT 1 — Siết Storage/Firestore rules + hạ tầng test emulator

## Mục tiêu
Đóng các lỗ hổng ở tầng rules (H1, H2 phần rules, H4, H5) và có bộ test chạy trên emulator để chứng minh.

## Phạm vi
Được sửa: `storage.rules`, `firestore.rules`, `firebase.json` (phần emulators), `package.json` (script + devDependency), `vitest*.config.ts`, thư mục `tests/rules/`, và mã client tối thiểu để khớp đường dẫn Storage mới.
KHÔNG làm ở prompt này: chat (Prompt 3), pipeline upload (Prompt 4), API (Prompt 2).

## Các bước

### 1. Hạ tầng test (làm trước)
- Thêm `@firebase/rules-unit-testing` vào devDependencies. Chọn phiên bản tương thích với phiên bản `firebase` đang cài (đọc peerDependencies, ghi lý do vào report).
- Trong `firebase.json` đảm bảo có emulator `firestore` và `storage` (giữ port hiện có).
- Tạo `vitest.rules.config.ts`: `include: ['tests/rules/**/*.test.ts']`, chạy tuần tự (`fileParallelism: false`), `testTimeout: 20000`. Cấu hình `vitest` mặc định phải `exclude` `tests/rules/**` để `npm test` không cần emulator.
- Thêm script: `"test:rules": "firebase emulators:exec --only firestore,storage --project demo-chopass \"vitest run -c vitest.rules.config.ts\""`. Dùng project id `demo-*` để không chạm project thật. Cần Java 11+, ghi vào README.
- `tests/rules/helpers.ts`: khởi tạo test env đọc `firestore.rules` và `storage.rules` từ đĩa; hàm tạo context theo `uid` và custom claims (`verified`, `admin`); hàm seed dữ liệu bằng `withSecurityRulesDisabled`.
- Nếu emulator Storage không chạy được cross-service `firestore.get`/`firestore.exists` ở một ca nào đó, ghi rõ ca đó trong report và đề xuất cách kiểm thay thế. Không bỏ qua im lặng.

### 2. Viết test TRƯỚC (phải fail với rules hiện tại)
Các ca phải bị TỪ CHỐI:
- User B (verified) ghi đè hoặc xóa ảnh trong thư mục của User A.
- User chưa verified upload ảnh tin đăng.
- Upload ảnh tin đăng > 5MB; contentType không phải jpeg/png/webp; tên file không đúng mẫu.
- Update một file ảnh tin đăng đã tồn tại (kể cả của chính mình).
- User đọc `private/cards/{uidKhác}`; user đọc doc `verifications/{uidKhác}`.
- Ghi vào `public/avatars/{uidKhác}`; avatar > 2MB.
- Xóa ảnh thẻ khi hồ sơ đang `pending` hoặc `approved`.
- Favorite/follow: update đổi `userId`; create với `userId` của người khác; thừa key lạ; `createdAt` khác `request.time`.
Các ca phải được PHÉP: chủ tin upload ảnh hợp lệ vào thư mục của mình; chủ tin xóa ảnh của mình; admin xóa ảnh; đọc ảnh công khai khi chưa đăng nhập; user tự cập nhật avatar; user xóa favorite của mình; xóa ảnh thẻ khi chưa nộp hồ sơ hoặc hồ sơ `rejected`.

### 3. Sửa `storage.rules`
- Quy ước đường dẫn mới: `public/listings/{userId}/{draftId}/{fileName}` (`draftId` là UUID v4 do client sinh mỗi phiên đăng tin; Prompt 2 sẽ dùng nó làm id tin).
- Cho phép `create` (không cho `update`), delete theo chủ hoặc admin. Mẫu tham khảo, điều chỉnh theo code thật:
  ```
  function isValidImage(maxBytes) {
    return request.resource.contentType.matches('image/(jpeg|png|webp)')
      && request.resource.size <= maxBytes;
  }
  match /public/listings/{userId}/{draftId}/{fileName} {
    allow read: if true;
    allow create: if isOwner(userId) && isVerified()
      && isValidImage(5 * 1024 * 1024)
      && fileName.matches('[A-Za-z0-9_-]{8,64}\.(webp|jpg)');
    allow update: if false;
    allow delete: if isOwner(userId) || isAdmin();
  }
  ```
- Avatars: tên file cố định `avatar.webp` (cho phép update để đổi avatar), tối đa 2MB, chỉ chủ tài khoản. Ghi chú trong code client: thêm `?v=<updatedAt>` để tránh cache cũ.
- Ảnh thẻ `private/cards/{userId}/{fileName}`: chỉ `create` (không update), tên file ngẫu nhiên theo mẫu, ≤10MB. `delete` cho phép admin, hoặc chủ khi KHÔNG tồn tại hồ sơ hoặc hồ sơ `rejected`. Lưu ý `firestore.get` lỗi nếu doc không tồn tại, nên bọc bằng `firestore.exists(...)` trước.
- Không động tới `private/chats` (Prompt 3).
- Ghi chú trong file: rules không giới hạn được số lượng file ⇒ quota phải kiểm ở API (Prompt 2) và dọn rác định kỳ (Prompt 8).

### 4. Sửa `firestore.rules`
- `favorites` và `follows`: tách `allow read, write` thành `read` (theo `userId`/`followerId`), `create` (ép `userId == auth.uid`, `keys().hasOnly([...])` theo field thực tế, độ dài id ≤128, `createdAt == request.time`), `update: false`, `delete` (theo chủ). Nếu code hiện dùng docId xác định (ví dụ `${uid}_${listingId}`) thì ép luôn docId.
- `users`: dựa vào kết quả Q6. Nếu doc có PII (email, SĐT, MSSV, trạng thái duyệt, đường dẫn ảnh thẻ...), tách phần công khai ra (`displayName`, `photoURL`, `schoolCode`, `createdAt`, huy hiệu) và chuyển PII sang `usersPrivate`; cập nhật mọi chỗ đọc/ghi. Nếu không có PII, ghi "Không áp dụng" kèm bằng chứng.

### 5. Cập nhật client tối thiểu
Tìm mọi chỗ dùng `public/listings/` và đổi sang đường dẫn mới để build và test cũ vẫn xanh. Chưa cần làm UX upload mới (Prompt 4), chỉ đổi path và sinh `draftId`.

### 6. Chạy toàn bộ gate (gồm `npm run test:rules`), commit.

## Nghiệm thu

# PROMPT 2 — Hardening API Routes

## Mục tiêu
Mọi quyết định bảo mật nằm ở server, nhất quán, có test: xác thực, verified, validate input, rate limit bền, idempotency. Áp dụng cho `/api/listings/create`, `/api/listings/contact`, `/api/verifications/submit` và các route còn lại trong ma trận Prompt 0.

## Phạm vi
Được sửa: `src/app/api/**`, `src/lib/server/**` (tạo mới), `tests/**`, và code client gọi API nếu hợp đồng request/response đổi.
KHÔNG làm: chat (Prompt 3), pipeline upload client (Prompt 4), logic duyệt thẻ và cron (Prompt 5).

## Các bước

### 1. Hạ tầng dùng chung `src/lib/server/`
- `http.ts`: lớp `ApiError(status, code, message)`; `withApi(handler)` bắt lỗi (ApiError → đúng mã; ZodError → 400 với danh sách lỗi rút gọn; lỗi lạ → 500 chung chung, log phía server không kèm PII); `readJson(req, maxBytes = 64 * 1024)` kiểm tra content-type và kích thước (413 khi vượt).
- `auth-guard.ts`: 
  - `requireAuth(req)`: lấy Bearer token, `verifyIdToken(token, true)` (checkRevoked, cũng bắt user bị disable) → 401 nếu lỗi.
  - `requireVerified(req)`: sau `requireAuth`, đọc trạng thái verified từ Firestore làm nguồn sự thật (dùng đúng nơi admin approve đang ghi, xem Q1; nếu có hai nơi lệch nhau thì ghi vào report và dùng `verifications/{uid}.status === 'approved'`). KHÔNG tin body, header, localStorage hay claim cũ.
  - `requireAdmin(req)`: claim admin từ token đã verify.
  - Nếu Q16 cho thấy dùng cookie session: thêm `assertSameOrigin(req)` cho mọi method khác GET. Nếu dùng Bearer thì ghi "CSRF không áp dụng".
- `rate-limit.ts`: `consumeRateLimit({ scope, key, limit, windowSec })` bằng Firestore transaction trên `rateLimits/{scope}_{key}_{windowStart}` (fields `count`, `expiresAt`); vượt thì `ApiError(429)` kèm header `Retry-After`. Preset: xem liên hệ 10/giờ/uid (README), tạo tin 5/giờ/uid, nộp hồ sơ SV 3/ngày/uid. TUYỆT ĐỐI không dùng Map in-memory (vô tác dụng trên serverless).
- `schemas.ts`: các schema Zod `.strict()` dùng chung.
- Mọi route dùng firebase-admin phải có `export const runtime = 'nodejs'` và `export const dynamic = 'force-dynamic'`.
- Các collection mới (`rateLimits`, `idempotency`) chỉ Admin SDK ghi; rules default-deny đã bao phủ, hãy viết thêm một test rules xác nhận client không đọc/ghi được.

### 2. `/api/listings/create`
- Body theo schema `.strict()`; chỉ copy field được phép. KHÔNG spread body vào doc. `sellerId`, `status`, `createdAt`, `viewCount`, `searchTokens` do server gán. Giữ nguyên cấu trúc dữ liệu hiện có.
- Request mang `draftId` (UUID v4) và `images: string[]` là đường dẫn Storage. Server kiểm: từng path bắt đầu bằng `public/listings/${uid}/${draftId}/`, số lượng 3–10, không trùng, object tồn tại (`exists()` + metadata contentType là image). Id tin = `draftId`; nếu doc đã tồn tại thì trả 409.
- Giới hạn: title 5–80 ký tự, mô tả tối đa 2000, giá số nguyên 0–500.000.000 VND, category/trường/vùng nằm trong danh mục thật, `deadline` dạng `YYYY-MM-DD` trong khoảng hôm nay đến +90 ngày (tính theo giờ VN, xem Prompt 8 cho chi tiết múi giờ), enum cho tình trạng và hình thức giao nhận.
- Giới hạn "tối đa 10 tin đang bán" kiểm trong transaction (query `sellerId == uid` và `status in [active, reserved]`, `limit(10)`). Rate limit 5 tin/giờ khống chế phần race còn lại, ghi chú điều này trong code.
- Idempotency: header `Idempotency-Key` (UUID). Ghi doc `idempotency/{uid}_{key}` (kèm `expiresAt` +24h) CÙNG transaction với việc tạo tin. Gọi lại cùng key thì trả lại kết quả cũ, không tạo tin thứ hai.
- Cấu hình `BLOCK_CONTACT_IN_PUBLIC_TEXT = true` trong `src/config/`: nếu title/mô tả chứa SĐT Việt Nam hoặc link `zalo.me` thì trả 422 với thông báo "Vui lòng không ghi số điện thoại/Zalo trong mô tả. Người mua đã xác minh sẽ xem được liên hệ của bạn." Ghi vào "Quyết định cần xác nhận".

### 3. `/api/listings/contact`
- Chỉ POST `{ listingId }`; GET trả 405.
- Thứ tự: `requireVerified` → nếu đã có log `contactViewLogs/{uid}_{listingId}` thì trả lại liên hệ mà KHÔNG trừ quota (xem lại không bị phạt) → ngược lại `consumeRateLimit` → transaction kiểm tin.
- Điều kiện: tin `active`; hoặc `reserved` và người gọi là người đang giữ chỗ hợp lệ; người gọi khác người bán; người bán không bị khóa. Không thỏa ⇒ 404 (không phân biệt "không tồn tại" và "không được xem").
- Ghi `contactViewLogs/{uid}_{listingId}` (viewerId, sellerId, listingId, firstViewedAt, viewCount) trong cùng transaction.
- Response luôn có `Cache-Control: no-store`.

### 4. `/api/verifications/submit`
- Path ảnh phải bắt đầu bằng `private/cards/${uid}/`; kiểm tra object tồn tại, contentType image, kích thước ≤10MB bằng metadata ở server.
- Chặn nộp lại khi đang `pending`; chặn ghi đè khi đã `approved`; cho nộp lại khi `rejected`.
- Dedupe HMAC-SHA256 (secret từ env, không hardcode): dùng doc `studentIdHashes/{hash}` làm khóa duy nhất trong transaction. Khi trùng trả 409 với thông báo chung "Thông tin này không thể dùng để xác minh. Vui lòng liên hệ hỗ trợ." KHÔNG tiết lộ tài khoản nào đang giữ MSSV.
- Rate limit 3/ngày. Không log MSSV hay đường dẫn ảnh.

### 5. Các route còn lại
Với từng route trong ma trận Prompt 0 (`listings/manage`, `reservations/*`, `reviews`, `reports`, `appeals`, `account/delete`, `admin/*`...): thay logic auth tự viết bằng helper, thêm Zod `.strict()` nếu thiếu, đảm bảo `uid`/`sellerId` lấy từ token. KHÔNG đổi hành vi nghiệp vụ.

### 6. Test (Vitest, theo mẫu mock firebase-admin đang có trong `api-auth-guards`)
Tối thiểu: không token → 401; token revoke/disabled → 401; chưa verified → 403; body có `sellerId` giả bị bỏ qua hoặc bị 400 do `.strict()`; body > 64KB → 413; vượt rate limit → 429 có `Retry-After`; create với path ảnh của người khác → 400; create trùng `draftId` → 409; create hai lần cùng Idempotency-Key → 1 tin; create khi đã đủ 10 tin → 409; create có SĐT trong mô tả → 422; contact tin không active → 404 và có `no-store`; contact GET → 405; xem lại liên hệ không trừ quota; submit hồ sơ trùng hash → 409 với thông báo chung; submit path ảnh của người khác → 400.

### 7. Chạy toàn bộ gate, commit.

## Nghiệm thu
Không route nào còn tự parse token riêng; không còn rate limit in-memory; mọi test ở bước 6 pass.

# PROMPT 3 — Hardening chat (H3)

## Mục tiêu
Chỉ người đã verified mới mở được hội thoại; tin nhắn hợp lệ nghiêm ngặt; không còn khoảng trống để vòng qua cơ chế ẩn liên hệ bằng spam; ảnh chat an toàn.

## Phạm vi
Được sửa: collection `conversations`/`messages` trong `firestore.rules`, `private/chats` trong `storage.rules`, route mới `/api/conversations/create`, màn hình `/messages` và component chat, test.
KHÔNG làm: thêm tính năng mới (report, chặn người dùng, v.v.) ngoài những gì liệt kê dưới đây.

## Các bước

### 1. Đọc chat hiện tại
Ghi vào report: cấu trúc doc conversation/message hiện có, nơi client ghi trực tiếp, cách sinh id hội thoại.

### 2. Viết test rules TRƯỚC (phải fail với rules hiện tại)
Phải bị TỪ CHỐI: client tạo conversation trực tiếp; message có `createdAt` ≠ `request.time`; text rỗng hoặc >1000; key lạ trong message; `senderId` khác `auth.uid`; user không thuộc hội thoại đọc/ghi message; update/xóa message; update conversation làm đổi `participantIds` hoặc field ngoài whitelist; `imagePath` không thuộc `private/chats/{convId}/`; upload ảnh chat không phải participant, >3MB, tên file sai mẫu, update file đã có.
Phải được PHÉP: participant gửi message hợp lệ; participant đọc; participant cập nhật `lastMessage`/`updatedAt`/`readBy`; participant upload ảnh chat hợp lệ.

### 3. API `/api/conversations/create` (POST `{ otherUserId, listingId? }`)
- `requireVerified`; từ chối nếu `otherUserId === uid`, người kia không tồn tại hoặc bị khóa.
- Nếu có `listingId`: tin phải `active` và `sellerId === otherUserId`.
- Id hội thoại xác định: `sorted([uidA, uidB]).join('_') + (listingId ? '_' + listingId : '')`. Tạo trong transaction nếu chưa có, ngược lại trả hội thoại cũ (không tạo trùng).
- Doc chỉ gồm field whitelist: `participantIds` (2 phần tử khác nhau), `listingId?`, `createdAt`, `updatedAt`, `lastMessage`, `readBy`.
- Rate limit: 20 hội thoại mới/ngày/uid.

### 4. Sửa rules
- `conversations`: `create: false`; `read` theo participant/admin; `update` chỉ cho `participantIds` bất biến và `affectedKeys().hasOnly(['lastMessage','updatedAt','readBy'])`; `delete` chỉ admin.
- `messages`: `create` bắt buộc:
  ```
  isAuthenticated()
  && request.auth.uid in get(/databases/$(database)/documents/conversations/$(convId)).data.participantIds
  && request.resource.data.keys().hasOnly(['senderId','text','createdAt','imagePath'])
  && request.resource.data.senderId == request.auth.uid
  && request.resource.data.text is string
  && request.resource.data.text.size() >= 1 && request.resource.data.text.size() <= 1000
  && request.resource.data.createdAt == request.time
  && (!('imagePath' in request.resource.data)
      || request.resource.data.imagePath.matches('private/chats/' + convId + '/[A-Za-z0-9_-]{8,64}\.(webp|jpg)'))
  ```
  (Điều chỉnh nếu tin chỉ có ảnh không có text; không nới lỏng các điều kiện còn lại.)
- `storage.rules` `private/chats/{chatId}/{fileName}`: `read` và `create` cho participant (qua `firestore.get` kèm `exists`), `create` chỉ khi `isValidImage(3MB)` và tên file đúng mẫu, `update: false`, `delete` chỉ admin.

### 5. Client
- Mở hội thoại bằng cách gọi API ở bước 3 (có `Authorization` Bearer), không ghi `conversations` trực tiếp.
- Gửi tin dùng `serverTimestamp()`; ảnh lưu `imagePath`, lấy URL bằng `getDownloadURL` khi hiển thị.
- Hiển thị text bằng React (không `dangerouslySetInnerHTML`); không tự biến văn bản thành link.
- Banner cố định đầu khung chat: "Không chuyển khoản đặt cọc trước. Hẹn gặp ở nơi công cộng như cổng trường, KTX."
- `onSnapshot`: `limit(50)`, `orderBy('createdAt','desc')`, nút "Tải thêm", và PHẢI unsubscribe khi unmount.
- Người dùng chưa verified bấm "Nhắn tin" thấy hộp thoại dẫn tới onboarding, không bị lỗi trần.

### 6. Chạy toàn bộ gate, commit.

## Nghiệm thu
Mọi ca ở bước 2 có test (fail trước, pass sau). Client không còn `setDoc/addDoc` vào `conversations`. Không còn listener Firestore rò rỉ khi rời màn chat.
Đọc và tuân thủ tuyệt đối `docs/HARDENING_RULES.md`, rồi đọc `docs/AUDIT.md` (Q2, Q3, H8, H9, H16). Checkout `hardening/all`. Prompt 1 và 2 đã xong: đường dẫn ảnh mới là `public/listings/{uid}/{draftId}/{fileName}`; `/api/listings/create` nhận `draftId`, `images[]` (storage paths) và `Idempotency-Key`.

# PROMPT 4 — Làm lại pipeline upload ảnh tin đăng

## Mục tiêu
Nút đăng tin không treo, ảnh không bao giờ bị nhét inline vào Firestore, chạy ổn trên mạng 4G chậm, iPhone/Safari và máy Android yếu.

## Phạm vi
Được sửa: bước 1 của `/listings/new`, các hàm nén/upload ảnh, hook/state liên quan, test. KHÔNG làm: các bước 2–5 của form (Prompt 6), thay đổi rules (đã xong).

## Các bước

### 1. Loại bỏ fallback inline
Tìm mọi chỗ dùng data URL/base64 cho ảnh tin đăng (kể cả khi hiển thị). Xóa hẳn đường fallback "ảnh WebP nén trực tiếp" cùng test ràng buộc nó. Lý do để ghi vào code comment và report: doc Firestore giới hạn 1MiB, mọi lần đọc feed sẽ tải cả ảnh, và body request của function trên Vercel bị giới hạn ở 4,5MB nên không thể đẩy ảnh qua API.

### 2. Module nén ảnh `src/lib/image/compress.ts`
Tách thành hàm thuần dễ test + phần dùng canvas:
- Validate đầu vào: type thuộc `image/jpeg|png|webp` (HEIC/khác thì báo "Định dạng ảnh chưa được hỗ trợ, hãy chọn JPG/PNG"), kích thước file ≤ 25MB (tránh tràn bộ nhớ).
- Giải mã: ưu tiên `createImageBitmap(file, { imageOrientation: 'from-image' })`; nếu trình duyệt không hỗ trợ tùy chọn thì fallback `<img>` + `decode()`. Luôn `bitmap.close()` và `URL.revokeObjectURL` sau khi dùng.
- Giữ tỉ lệ gốc; cạnh dài tối đa 1600px (hàm thuần `computeTargetSize(w, h, maxEdge)` có test). Vẽ thẳng lên canvas kích thước đích (không vẽ ảnh gốc khổng lồ rồi mới thu nhỏ).
- Mã hóa: thử `image/webp` quality 0.8, rồi **kiểm tra `blob.type`**. Nếu không phải `image/webp` (Safari/iOS có thể trả PNG) thì encode lại `image/jpeg` quality 0.82. Hàm thuần `pickOutputFormat(blobType)` có test.
- Nếu blob > 1,5MB thì giảm quality theo bậc (0.7 → 0.6 → 0.5); nếu vẫn >5MB thì báo lỗi rõ ràng.
- Quyết định sản phẩm (ghi vào report): KHÔNG crop cứng 4:3. Thẻ tin dùng CSS `aspect-ratio: 4/3` + `object-cover`, trang chi tiết dùng `object-contain`. Ảnh bìa vẫn chọn bằng ngôi sao.
- Nén tuần tự từng ảnh (1 lúc 1 ảnh) để tránh tràn RAM.

### 3. Hàng đợi upload (state machine)
Mỗi ảnh có trạng thái: `queued → compressing → uploading(progress%) → done | error(reason)`.
- `draftId = crypto.randomUUID()` khi mở form (giữ nguyên trong phiên); tên file `${crypto.randomUUID()}.webp|jpg` (khớp mẫu rules).
- Upload bằng `uploadBytesResumable`, tối đa 2 ảnh song song (hàm `runPool` có test).
- KHÔNG có timeout tổng 1,2s. Thay bằng: phát hiện đứng hình khi 20 giây không có tiến trình thì hủy và đánh dấu `error`; tự thử lại tối đa 3 lần với backoff (1s, 3s, 7s) cho lỗi mạng; sau đó hiện nút "Thử lại" ở đúng ảnh lỗi.
- Phân loại lỗi hiển thị: `storage/unauthorized` ⇒ gọi `getIdToken(true)` đúng một lần rồi thử lại (claim `verified` có thể cũ), nếu vẫn lỗi thì thông báo cần xác minh thẻ SV; `storage/bucket-not-found`/lỗi cấu hình ⇒ "Hệ thống lưu ảnh đang bảo trì, vui lòng thử lại sau" (và log phía client không kèm PII); `storage/canceled` ⇒ bỏ qua; mất mạng ⇒ "Mất kết nối, ảnh sẽ tự thử lại".
- Nút "Tiếp tục" của bước 1 chỉ bật khi ≥3 ảnh `done` và không còn ảnh `compressing/uploading`. Hiển thị tiến trình tổng và từng ảnh.
- Xóa ảnh trong form: nếu đã `done` thì gọi `deleteObject` (rules cho phép chủ xóa). Hủy cả form: xóa các ảnh đã upload (best effort, lỗi thì bỏ qua; Prompt 8 có cron dọn rác).
- Lưu danh sách `{draftId, paths}` vào localStorage (khóa theo uid, TTL 24h) để tải lại trang không mất ảnh đã upload; hiển thị lại bằng `getDownloadURL`.

### 4. Nối với API
Khi đăng tin gửi `draftId`, `images` (paths theo thứ tự, ảnh bìa đứng đầu hoặc có `coverIndex`, theo hợp đồng Prompt 2), `Idempotency-Key` sinh một lần khi mở form. Nút "Đăng tin" vô hiệu khi đang gửi, có thông báo lỗi tiếng Việt cho 401/403/409/422/429; 429 đọc `Retry-After`.

### 5. Input chọn ảnh
`accept="image/jpeg,image/png,image/webp"`, `multiple`; cho phép chụp trực tiếp trên điện thoại. Giới hạn tổng 10 ảnh; chọn quá sẽ báo và chỉ nhận phần còn trống.

### 6. Test (Vitest)
Hàm thuần: `computeTargetSize`, `pickOutputFormat`, `runPool` (giới hạn song song, thứ tự), reducer trạng thái hàng đợi (chuyển trạng thái, retry, stall), phân loại lỗi Storage, `canSubmit`. Không thêm thư viện test DOM nếu chưa có; phần canvas được mock ở mức tối thiểu hoặc ghi chú "kiểm tra tay trên thiết bị thật".

### 7. Chạy toàn bộ gate, commit.

## Nghiệm thu
Không còn data URL cho ảnh tin; không có timeout cứng 1,2s; nút đăng tin không treo vô hạn trong mọi kịch bản lỗi; thêm file `docs/MANUAL_QA.md` mục "Upload ảnh" liệt kê các ca cần chủ dự án thử tay: iPhone Safari, Android Chrome, giả lập 4G chậm, tắt mạng giữa chừng, chọn ảnh HEIC, chọn ảnh >25MB.

## Việc chủ dự án tự làm (ghi vào report)
Xác nhận production đã tạo Storage bucket (cần gói Blaze) và đã deploy `storage.rules` mới.
Đọc và tuân thủ tuyệt đối `docs/HARDENING_RULES.md`, rồi đọc `docs/AUDIT.md` (Q1, Q4, Q5, Q11, H6, H7, H10). Checkout `hardening/all`. Prompt 1 và 2 đã xong.

# PROMPT 5 — Xác thực, xác minh SV, vòng đời ảnh thẻ

## Mục tiêu
Trạng thái verified nhất quán và chỉ tin ở server; email `.edu.vn` không bị bypass; admin duyệt thẻ có dấu vết; ảnh thẻ thật sự bị xóa sau 30 ngày.

## Phạm vi

## Các bước

### 1. Hàm `isStudentEmail` thuần có test

## Các bước

### 1. Giữ chỗ (reservation)
Đọc kỹ code hiện tại (Q9), sửa theo thực trạng:
- Tạo giữ chỗ trong một Firestore transaction: kiểm tin còn `active`, chưa có giữ chỗ mở, người giữ ≠ người bán, người giữ đã verified. Hai người bấm cùng lúc thì chỉ một người thành công, người kia nhận 409 "Món đồ vừa được người khác giữ chỗ."
- Máy trạng thái hợp lệ: `active → reserved → sold`; `reserved → active` khi hủy hoặc hết hạn. Chặn mọi chuyển trạng thái khác ở server (ví dụ `sold → active`).
- Hạn giữ chỗ: `expiresAt` (mặc định 24 giờ, đặt trong `src/config/`). Hàm `expireIfNeeded(tx, reservation)` chạy khi đọc/tạo/thao tác (lazy expire) + cron `/api/cron/expire-reservations` chạy hằng ngày để dọn phần còn sót.
- Mỗi người mua tối đa 2 giữ chỗ đang mở; vượt ⇒ 409.
- Đề xuất, KHÔNG code nếu chưa có sẵn: phạt "không đến" (đếm `noShowCount`, tạm khóa giữ chỗ 7 ngày sau 3 lần). Chỉ ghi vào report để chủ dự án quyết.
- Test: đua hai người giữ cùng lúc, hết hạn rồi giữ lại, vượt giới hạn 2, chuyển trạng thái sai, người bán tự giữ chỗ.

### 2. Múi giờ & hạn pass
`src/lib/time.ts`: `VN_TZ = 'Asia/Ho_Chi_Minh'`; `parseDeadlineVN('YYYY-MM-DD')` ⇒ thời điểm 23:59:59 giờ VN (Việt Nam không có giờ mùa hè nên dùng offset +07:00); `isExpiredVN(deadline, now)`; `formatVN(date)` bằng `Intl.DateTimeFormat('vi-VN', { timeZone: VN_TZ })`. Mọi tính toán hạn ở server dùng các hàm này (Vercel chạy UTC); client chỉ hiển thị. Nhãn "Pass trong ngày" dựa trên công tắc `urgent` do người đăng bật, hiển thị hạn tương đối ("còn 5 giờ"). Tin hết hạn: cron `/api/cron/expire-listings` chuyển `status` sang `expired` (feed chỉ lấy `active`), trang chi tiết hiện "Đã hết hạn" nếu quá hạn dù cron chưa chạy. Test: ranh giới nửa đêm (23:59:59 và 00:00:00 giờ VN), UTC lệch ngày, năm nhuận.

### 3. Xóa tài khoản (`/api/account/delete`)
Idempotent và có thể chạy lại khi lỗi giữa chừng (đánh dấu `deletionStartedAt`):
1. Hủy giữ chỗ đang mở và thông báo bên còn lại.
2. Chuyển tin đang đăng sang `removed`, xóa ảnh trong `public/listings/{uid}/`.
3. Xóa favorites, follows, notifications của user; xóa hồ sơ `verifications`, `usersPrivate`, ảnh thẻ, ảnh đại diện.
4. Ẩn danh hóa thay vì xóa review/tin nhắn của người khác (đổi tên hiển thị thành "Người dùng đã xóa", bỏ `photoURL`).
5. `users/{uid}`: đặt `deleted: true` và xóa thông tin định danh; cuối cùng `auth.deleteUser(uid)`.
Dùng batch tối đa 400 thao tác mỗi lượt. Test với admin mock: chạy lại lần hai không lỗi, ẩn danh đúng, không xóa nhầm dữ liệu người khác.

### 4. Dọn ảnh rác
Cron `/api/cron/cleanup-orphan-images` (hằng ngày): liệt kê thư mục `public/listings/{uid}/{draftId}/` cũ hơn 24 giờ mà không có doc `listings/{draftId}`, xóa; mỗi lần tối đa 500 file; log số lượng. Thêm cả ba cron mới vào `vercel.json`. Test hàm thuần chọn thư mục mồ côi.

### 5. Các điểm còn lại
- Danh mục "Xe cộ": đã có cảnh báo ở Prompt 6; không thêm gì ở server.
- Xác minh lại hằng năm cho SV đã ra trường: chỉ ghi đề xuất vào report (`verifiedAt`, `reverifyAfter`), không code.

### 6. Nghiệm thu toàn bộ
- Chạy: `npx tsc --noEmit`, `npm run lint`, `npm test`, `npm run test:rules`, `npm run build`, `npm audit --omit=dev`. Chép kết quả (số test, số route build) vào report.
- Quét sót: không còn `data:image`/base64 trong luồng tin đăng; không còn `localStorage` ở logic quyết định bảo mật; không còn `console.log` chứa dữ liệu người dùng; không còn Map in-memory làm rate limit; không còn đường dẫn `public/listings/{listingId}/` kiểu cũ.
- Hoàn thiện `docs/MANUAL_QA.md` (10–15 kịch bản chủ dự án tự thử): đăng nhập Google, nộp hồ sơ thẻ, admin duyệt, đăng tin có ảnh trên iPhone và Android (4G chậm), xem liên hệ khi chưa/đã verified, giữ chỗ từ hai tài khoản cùng lúc, chat có ảnh, xóa tài khoản, chia sẻ link tin vào Zalo xem preview, CSP không báo lỗi.
- Cập nhật README cho khớp thực tế: script `test:rules`, đường dẫn Storage mới, các cron và biến môi trường, danh mục việc cần làm trước khi mở cho người dùng thật.
- Hoàn thiện `docs/HARDENING_REPORT.md` với phần tổng hợp đầu file: bảng H1–H16 (trạng thái cuối), tổng hợp "Việc chủ dự án tự làm" theo ĐÚNG THỨ TỰ deploy:
  1. `firebase deploy --only firestore:rules,firestore:indexes,storage`
  2. Đặt biến môi trường trên Vercel (`STUDENT_ID_HMAC_SECRET`, `CRON_SECRET`, `ADMIN_EMAIL`, `NEXT_PUBLIC_SITE_URL`, project id).
  3. Bật Firestore TTL (`rateLimits`, `idempotency`), áp lifecycle bucket 30 ngày, tạo Storage bucket nếu chưa có.
  4. Bật 2FA cho admin, đặt budget alert.
  5. Deploy Vercel rồi chạy `docs/MANUAL_QA.md`.
- Tổng hợp "Quyết định cần chủ dự án xác nhận" và "Phát hiện thêm".

## Nghiệm thu
Mọi gate xanh; `docs/HARDENING_REPORT.md` đầy đủ; không còn mục nào ở H1–H16 ở trạng thái chưa kết luận.
